# Архитектура

Документ для того, кто будет это продолжать. Отвечает на вопрос «почему так»,
а не «что где лежит» (это в README).

## 0. Уроки аудита кода (проведён на 7 768 строках, 37 файлах)

Аудит искал не стиль, а **места, где код врёт о себе**. Нашлось четыре класса, и все
четыре стоит помнить, потому что каждый уже случился:

1. **Мёртвая абстракция.** `EventBus` был автозагружаемым узлом с сигналом, логом и
   методом `emit_battle`, который не вызывал **никто**: реальный поток событий шёл
   через `BattleEngine.take_events()`. Удалён. Абстракция без подписчика хуже
   отсутствующей — она уводит того, кто ищет, где же события.
2. **Проверка, сторожащая мёртвый код.** Команда `--swap` гоняла
   `swap_weapon(cost_turn = true)`, которого экран не звал: механика «смены за ход»
   перестала существовать, а проверка оставалась зелёной и **давала ложную
   уверенность**. Переписана на боевой путь. Правило: проверка обязана вызывать то,
   что вызывает игра.
3. **Два и более источников правды.** Оружие жило в четырёх местах (движок, `hunter`,
   `GameState`, экран), а дальность и тип удара передавались в `submit_read`
   ПАРАМЕТРАМИ, хотя движок знал их из оружия. Согласованность держалась не
   инвариантом, а тем, что экран выставлял их правильно. Теперь источник один —
   оружие, остальное производное.
4. **Мёртвая ветка внутри живого метода.** Навык «Быстрая смена» расходовался в двух
   местах: в боевом пути (работает) и в старом `swap_weapon` (недостижим). Две
   реализации одной механики означают, что одна из них устареет первой.

Дополнительно найдено и исправлено: **дубль тикающего урона** (он списывался и в
`submit_read`, и в `_round_end` — то есть при пути «через чтение» дважды), **потеря
второго типа урона в подборе комбо** (зачарованный молот переставал давать комбо на
дробящий, хотя урон по дробящему шёл) и **мусор от `--probe`** (`_probe.tres`
оставался в папке проекта и грузился следующим запуском).

Что аудит **не** подтвердил, хотя выглядело подозрительно: циклов зависимостей в
`core/` нет — `WeaponData → CityData`, `Outcome → MarketData`, `battle_engine →
HuntResult` оказались упоминаниями в комментариях, а не кодом. Урок: проверять
гипотезу до того, как называть её находкой.

### 0.1 Проверки живут отдельно от точки входа

`main.gd` был 875 строк, из них больше половины — проверки, перемешанные с
рантаймом. Теперь точка входа **107 строк** и не содержит ни одной проверки: она
разбирает аргументы и зовёт.

| Где | Что | Почему здесь |
|---|---|---|
| `core/sim/checks/report.gd` | одна точка записи отчётов | 18 копий `_write_out` с абсолютным путём внутри — это то, что нельзя поменять одной правкой |
| `core/sim/checks/logic_checks.gd` | `validate`, `outcomes`, `swap`, `art`, `repeat`, `prose`, `probe`, `sim`, `loop` | считаются на ядре, сцен не трогают |
| `ui/checks/ui_checks.gd` | `prep`, `smoke`, `measure_ui`, `capture_shots` | нужны сцены и дерево узлов |

**Граница проходит по сценам, а не по «важности».** `core/` обязан оставаться без
Node, поэтому проверка экрана не может там жить. Каждый метод `ui_checks` принимает
`host: Node` — так точкой входа не обязана быть та, кто выполняет.

**Имена отчётов не менялись** (`_validate_out.txt` и так далее): на них завязаны
`tools/run_headless.ps1` и рабочие привычки. Менять их — отдельное решение, а не
побочный эффект переноса.

**Найденный дефект по ходу.** `--probe` писал `_probe.tres` в папку проекта и не
удалял: Godot видел этот файл как контент, и следующий запуск грузил мусорный вид.
Теперь проверка убирает за собой.

### 0.2 Разбор аргументов не имеет права молча давать ноль

Самый дорогой баг аудита нашёлся **после** аудита, при переносе проверок.

`--loop` принимает число: `--loop 10`. Разбор был написан как `int(args[i + 1])`, и
когда за флагом шёл не число, а другой флаг, приведение давало **ноль**:

```
--loop --log-file F:\...\_glog.txt     →   hunts = 0
```

Симулятор честно прогонял **ноль охот**. Все контрольные суммы сходились на пустоте
(«сумма исходов 0, боёв 0 — сходится»), «ЛЕГЕНДА НЕ ДОСТИГНУТА» тоже выглядело
нормальным сообщением, и отчёт печатался. Проверка, которая ничего не проверяет,
выглядела зелёной.

**Почему это не всплыло раньше.** `tools\run_headless.ps1` зовёт `--loop` без числа
сразу за ним идёт `--log-file`, то есть полный прогон всегда шёл с нулём охот.
Отдельные ручные запуски с `--loop 10` работали, поэтому дефект не замечался ни
разу — до тех пор, пока трасса прогона не показала `hunts=0`.

**Исправлено:** `_int_arg()` принимает значение только если оно `is_valid_int()`,
иначе берётся значение по умолчанию. «Молчаливый ноль хуже падения» — теперь это
правило для всех числовых аргументов проверок.

**Заодно выяснилась цена режимов**, которая была скрыта тем же нулём: `--sim` на
200 боях идёт **34 секунды**, на 2000 — около шести минут. Раньше он «проходил
мгновенно», потому что считал ноль боёв. Поэтому значение по умолчанию снижено до
200: режим остаётся в быстром наборе, а глубокий анализ зовётся явно
(`--sim --battles 2000`).

## 1. Ядро не знает о движке

`core/` — обычный GDScript без Node и сцен. Из этого следует всё остальное:

- **Симулятор возможен.** 20 000 боёв прогоняются за секунды в `--headless`.
  GDD 12.11 проверял баланс руками и трижды ошибся в арифметике — здесь числа
  считаются настоящими формулами, с настоящим выбором сценариев и промахами.
- **Баги воспроизводимы.** Сид + лог событий → тот же бой.
- **Тесты не требуют UI.** Сборку прозы можно проверить ассертами.

Правило: если в `core/` появляется `Node` или `get_tree()` — это ошибка проекта.

## 2. Порядок раунда

```
1. Такт зверя (скрытый)   ScenarioPicker.pick()      — взвешенный выбор по характеру
2. Такт прозы (открытый)  TextGenerator.generate()   — опора + ложные следы
3. Такт решения (игрок)   BattleEngine.submit_read() — «что он сделает» + «чем отвечу»
4. Исход                  DamageCalc                 — 4 ступени, урон, статусы
```

**Раунд задаёт ДВА вопроса, и оба — решение.** «Что он сделает» (ставка на карточке)
и «чем я отвечу» (кнопка оружия). Ответы разные по цене:

| Ответ | Урон зверю | Урон охотнику |
|---|---|---|
| Ударить текущим оружием | есть | нет, если чтение верное |
| Взять другое оружие и ударить им | есть | нет, если чтение верное |
| **Сменить оружие или руну БЕЗ удара** | **нет — вот штраф смены** | **нет, если чтение верное** |
| То же, но с навыком «Быстрая смена» | **есть: навык снимает штраф** | как обычно |

**Верное чтение защищает в любом случае** — и когда бьёшь, и когда меняешь
инструмент. Знание защищает независимо от того, чем ты отвечал: это знание, а не
удар. Поэтому и разбор, и контр-приём, и снятие тумана считаются и в ход смены.

Навык «Быстрая смена» перехватывается **в ядре**, а не на экране: иначе он работал
бы в игре и не работал в прогоне. Расход — один за бой, сгорает независимо от
успеха чтения (смена уже произошла), и экран показывает готовность навыка ДО хода,
чтобы одноразовый эффект не выглядел случайностью.

**И это ЕДИНСТВЕННОЕ место, где навык расходуется.** Раньше вторая копия жила в
`swap_weapon(cost_turn = true)`, и та копия была недостижима из игры: экран её не
звал, её проверяла только команда `--swap`. То есть проверка была зелёной на мёртвом
коде. Теперь метода с оплатой ходом нет вообще (`equip_weapon` только меняет оружие),
а `--swap` гоняет боевой путь.

Почему цена смены именно такая. Раньше смена отнимала ОТДЕЛЬНЫЙ ход (зверь бьёт,
ты не бьёшь и ход потерян) — и тогда «чем бить» переставало быть решением: игрок
один раз настраивал оружие по досье и больше к нему не возвращался, а кнопка
инструмента всю охоту показывала одно и то же. Теперь цена — **отказ от удара в
этом ходу**, а не потеря темпа. Смена остаётся решением, но перестаёт быть
наказанием.

Отсюда же стартовая выдача ДВУХ оружий (лук и молот): с одним инструментом вопрос
«чем отвечу» не имеет вариантов ответа вообще.

**Дальность и тип удара в ядро НЕ передаются.** Ядро берёт их из оружия, которым
игрок отвечает. Раньше `submit_read` принимал `tool_range` и `tool_type`, и это
создавало второй источник правды: верность инструмента считалась по параметру, а
урон — по оружию. Значения совпадали лишь потому, что экран выставлял их
согласованно, — это не инвариант, а везение. Заодно исчезла и «верность
инструмента» как отдельная ступень: промахнуться инструментом теперь нельзя.

Движок копит события и отдаёт их через `take_events()`. Подписчики: экран боя
(рендерит) и симулятор (считает). Ядро не знает, кто именно слушает.

## 3. Детерминизм

```
seed_раунда = hash(run_seed, battle_index, round, salt)
```

`salt` разводит два потока:

- **mechanics** — выбор сценария, контр-приёмы, адаптация;
- **text** — выбор фраз.

Разделение обязательно. Без него выбор инструмента игроком сдвигает
последовательность фраз и ломает воспроизводимость.

`SeedSource` (в бою) и `RNGService` (в игре) решают одну задачу: первый —
локальный и полностью контролируемый, второй — глобальный между боями.

Почему `SeedSource` вообще появился: `RNGService` даёт один поток на бой, а раунду
нужен свой. Первая версия симулятора из-за этого гоняла один и тот же сценарий
все 7 раундов — это видно было только по дампу прозы.

## 4. Проза — структура, а не строка

`TextGenerator.generate()` возвращает:

```gdscript
{
  "lines": [
    {"slot": "pose",  "role": "core",  "signal_id": "hruz.pounce.pose",
     "label": "припадает к земле", "phrase_id": "hruz.pounce.pose.01",
     "text": "Тяжёлое тело опускается к самой воде..."},
    {"slot": "gaze",  "role": "decoy", ...},
  ],
  "core_labels": [...],   # для досье
  "prose": "...",         # готовый абзац
}
```

Из этой структуры бесплатно получаются:

- подсветка опорного сигнала (навык «Опорный сигнал», GDD 7.2);
- удаление ложного следа («Чистая проза»);
- разбор после боя («Память сигналов»);
- счётчик повторов фраз (критерий 13.2);
- локализация (текст — данные, а не литерал в коде).

Если бы генератор возвращал строку, всё это пришлось бы прикручивать сбоку.

## 5. Ложные следы привязаны к сценариям

Первая версия держала ложные следы на уровне вида. Дамп прозы сразу показал
проблему: один и тот же обман («Он замирает и смотрит сквозь тебя») лепился
к каждому сценарию из боя в бой.

Теперь `SignalData.scenario_id` у ложного следа заполнен, и у каждого сценария
свой пул обмана. Генератор берёт сначала «свои» следы, общие — только как запас.

Второе следствие: слот ложного следа не должен пересекаться с опорными слотами
**других** сценариев вида. Иначе в бою сложится пара «опора сценария A в слоте pose»
и «обман сценария B в слоте pose» — и игрок не сможет их различить. Именно это
и ловит инвариант 3 валидатора (он поймал три реальные ошибки при разработке).

## 6. Формулы

Ровно в одном месте — `core/battle/damage_calc.gd`:

```
Урон игрока = оружие + модификатор + чтение + комбо − панцирь зверя − резист
Урон зверя  = базовый урон или урон сценария − броня игрока
```

- «броня» — только игрок; защита зверя называется **панцирь** (правка GDD);
- модификатор: огонь +1, лёд и яд +0; уязвимость +1; резист −N;
- чтение: идеальное и полная контратака +1, частичное и промах +0;
- комбо: +2, только при идеальном чтении;
- **минимум 1 урона** за удар — непроходимых из-за округления боёв нет.

`DamageResult` хранит все слагаемые, а не только итог: принцип прозрачности
(GDD 12.1) требует показать игроку, откуда взялся урон.

## 7. Контр-приём

GDD 6.3 говорит «3× повтор», не уточняя, чей. Изначально я реализовал повтор
**зверя** — и это не сработало бы никогда: при весе 60% вероятность трёх прыжков
подряд всего 3.5%.

Реализовано как повтор **игрока**: три раза подряд назвал один сценарий — зверь
меняет повадку, а этот сценарий на 2 раунда получает вчетверо меньший вес.
Смысл — наказание за предсказуемость, а не за верное чтение.

## 8. Стены чтения и подсказка о тупике

Громун: резист к дальнему 2 + панцирь 2 съедают лук целиком (1 урона за раунд
против 15 HP). Это не загадка, а расход времени.

Поэтому в движке есть `_check_ineffective`: если инструмент дважды подряд даёт
минимальный урон, зверь сам показывает, что так его не взять. Это подсказка
о бесполезности **инструмента**, не о сценарии — знание всё ещё нужно.

## 9. Графика

Арт-поля объявлены с первого дня и не используются:

```gdscript
MonsterData.portrait        # карточка
MonsterData.by_scenario     # {"pounce": Texture2D} — контракт «сценарий → поза»
```

Экран боя трёхслойный: `ArtLayer` (сейчас пустой с плейсхолдером) → `HudLayer` →
`ProseLayer`. Зона под арт зарезервирована фиксированным размером, поэтому
добавление картинок не переломает вёрстку.

Контракт «сценарий → картинка» ложится на уже существующую модель: GDD 3.2 сам
говорит, что поза и снаряжение — визуальные слоты. То есть игрок прочитал присед
и увидел присед, без нового слоя данных.

## 10. Правило обманов: не по виду, а по сценарию

Это правило я понял не сразу и дважды переделывал разметку.

**Сначала** я запретил ложному следу занимать любой слот, который используется
опорным сигналом **вида**. Правило казалось строгим и безопасным — но оно
запрещает почти всё: у Громуна ядро занимает gear, pose, sound и environment,
свободным остаётся один gaze, а бюджет абзаца у продвинутого вида требует два
обмана на раунд. Контент в такое правило не влезает.

**Правильно** так: обман не должен делить слот с опорным сигналом **того сценария,
в котором он подмешивается**. Обман, привязанный к другому сценарию, в этом
сценарии не участвует — генератор его не берёт, значит и путаницы не создаёт.

Отсюда рабочая формула: для каждого сценария считаем свободные слоты
(дополнение к слотам его ядра) и требуем, чтобы обманов этого сценария было
не меньше бюджета абзаца (1 / 2 / 3 / 4 по рангу вида).

Валидатор проверяет ровно это. Именно он поймал все ошибки разметки — и это
лучший аргумент за то, что инварианты контента должны быть кодом, а не памяткой.

## 11. Потолок поглощения брони

`HunterState.ABSORPTION_CAP = 3`.

GDD 12.8 разрешает броню 1–3 плюс навык +1/+2/+3, то есть до 6. Симулятор показал
конкретное число: при поглощении 6 «мастерская» сборка получала **0 урона в 100%
боёв**, включая промахи — потому что поглощение выше урона сценария превращает
урон в `max(1, урон) = 1`, а любая броня сверх этого обнуляет и его.

Первая попытка поставить потолок 4 не помогла: 4 равно максимальному урону сценария
Хруза (прыжок), и непобедимость сохранялась. Потолок 3 работает, потому что он ниже
урона сценария **любого** вида: Хруз бьёт на 1, Ламент с захватом 7 — на 4.

Урок на будущее: потолок защиты надо выбирать по урону самого сильного зверя,
а не по стартовому. Если появятся виды с уроном сценария 3, потолок придётся
опускать до 2.

Побочный эффект, который стоит держать в голове: у Шипуна урон сценария 3, поэтому
сборка с поглощением 3 не получает от него урона вовсе. Для стартового вида это
нормальная кривая силы (полная прокачка Выживания стоит ~140 монет и ранг
«Ветеран»), но если у Шипуна должна быть своя угроза — ему нужен урон сценария 4.

## 12. Побег — третий исход, и это ловушка для отчётности

Побег живёт в ядре (`BattleEngine.attempt_escape`), а не в экране: шанс — боевое
правило, и симулятор обязан считать по нему же. Числа и их обоснование — в README.

Что важно архитектурно: **побег — это третий исход наравне с победой и поражением,
а не разновидность поражения.** Первая версия симулятора считала его так:

```gdscript
if engine.phase == PHASE_VICTORY: wins += 1
else: losses += 1        # ← побег попадал сюда
```

Отчёт показывал «100 поражений из 100 боёв» при 71 успешном побеге в тех же боях.
Лечится не подкруткой метрики, а явной веткой `elif engine.phase == PHASE_FLED`.
Правило на будущее: **новый исход боя — это правка всех трёх мест** — движок,
`HuntResult.apply`, все счётчики в симуляторах. Проверка простая: сумма
`победы + побеги + поражения` должна равняться числу боёв. Я добавил её в отчёт
(`escape_wins`, `escape_tries`, `total_rounds_played`) именно поэтому.

Вторая ловушка: `attempt_escape` вызывается в цикле и **не тратит раунд** (GDD 2.5:
«попытка не отменяет ход»). Значит, если игрок бьёт и бежит в одном раунде, любой
счётчик «действий за раунд» надо держать на стороне UI — в движке такой гарантии нет.
Поэтому на экране есть флаг `_escaped_this_round`.

## 13. Новые механики живут в ядре, числа — в константах

Инициатива, крит и оглушение добавлены туда же, где формулы урона: в `DamageCalc`
и `BattleEngine`, а не в экран. Причина всё та же — симулятор должен считать по тем
же правилам, иначе отчёт перестаёт быть проверкой игры.

Два места, где легко ошибиться:

- **Инициатива требует СТРОГОГО превосходства.** В GDD 2.6 сказано «равны — игрок
  бьёт первым», поэтому `monster.initiative > hunter.initiative()`, а не `>=`.
  Ошибка на один символ дала бы зверю лишний удар в каждом бою с равной инициативой.
- **Крит считается от оружия, а не от итогового урона.** Если множить итог, крит
  усилит и чтение, и комбо, и один удачный бросок решит бой. Поэтому в
  `DamageResult` есть отдельное поле `crit_bonus`, и он входит в сумму слагаемых
  наравне с остальными — это заодно сохраняет принцип прозрачности (GDD 12.1).

Проверка для любой новой механики: **включить её в отчёт счётчиком и убедиться,
что число не ноль и не бессмысленно.** Так нашлись сразу два дефекта: знак ранга,
которому я приписал +1 к инициативе (в GDD 8.7 этого нет), из-за чего превентивный
удар не срабатывал вообще; и инициатива, которая из-за тех же чисел оказалась
почти декоративной.

### 13.1 Название типа урона — только в CityData

`CityData.type_ru()` и `range_ru()` — единственное место, где тип урона и дистанция
превращаются в слова. Раньше `_type_ru` существовала **в четырёх копиях** (экран
боя, подготовка, город, `DamageCalc`, `DossierRecorder`), а `_range_ru` — **в
шести**.

Копии разъехались ровно так, как и должны были. Когда физический урон разделили на
подтипы, маппинг обновили в трёх копиях из четырёх — и экран боя начал подписывать
копьё «физикой», хотя `DamageCalc` считал его колющим:

```text
Раунд: 1 · Копьё (ближний, колющий) · инициатива 7 против 3   ← строка раунда
ЧЕМ БИТЬ?  ближний · физика · урон 3                          ← строка инструмента, ВРАЛА
```

Это тот же класс ошибки, что и с руной: **механика верна, врёт подпись** — а игрок
решает по подписи. Признак структурный, а не случайный: пока маппинг лежит в N
копиях, правка типа урона его обязательно разъедет.

Правило: добавил тип урона — добавь его в `CityData.type_ru()`, и он появится на
всех экранах. Локальные `_type_ru`/`_range_ru` в экранах и модулях оставлены как
делегаты, чтобы вызовы читались, но логики в них нет. Полная форма («ближний бой»)
берётся флагом `range_ru(id, true)` — она нужна там, где название входит в
предложение.

### 13.2 Как разрезан ui_data: четыре файла вместо одного

`CityData` был 868 строк и смешивал четыре несвязанные темы. Разрезан так, чтобы
каждый файл отвечал на один вопрос:

| Файл | Отвечает на вопрос | Строк |
|---|---|---|
| `city_data.gd` | сколько стоит заказ, сколько славы, сколько дней | 249 |
| `skills_data.gd` | что можно купить и что открывает руну | 163 |
| `dossier_text.gd` | что игрок знает о виде и как это назвать словами | 300 |
| `art_paths.gd` | какие картинки искать и в каком порядке | 57 |

Три правила, по которым проведена граница:

1. **Арт — не логика города.** Ни один расчёт баланса не обращается к картинкам,
   поэтому держать таблицу путей рядом с ценами значило заставлять читателя
   пролистывать шесть десятков строк про фоны, чтобы дойти до славы за победу.
2. **Навык — не досье.** Таблица навыков и правила покупки не знают про `GameState.dossier`,
   а досье не знает про цены. Единственная связь — руна: это навык, чей эффект
   накладывается на оружие, поэтому `RUNE_SKILLS` живёт в `skills_data.gd`.
3. **Названия типов остаются в `CityData`.** Соблазнительно унести их в `dossier_text.gd`
   (он их и правда использует), но тогда получается цикл: `CityData` зовёт
   `DossierText.dossier_view()`, а `DossierText` — `CityData.type_ru()`. Источник
   истины обязан быть тем, от кого зависят, а не тем, кто зависит.

**Строковый рендер досье (`dossier_lines`) удалён.** Его не звал ни один экран —
город и подготовка строят окно из `dossier_view()`. А проверка `--prep`, которая
его «сторожила», давала зелёный отчёт о функции, которую игрок никогда не видел:
ложная уверенность хуже отсутствия проверки. Валидатор переписан на структуру
(`view["attacks"]` и их улики), и проверка проверена на искусственной поломке —
24 срабатывания по числу атак.

### 13.3 Экономика: проверка цены и списание — одна операция

`GameState.spend_coins(cost)` — единственный способ убрать монеты из кошелька,
кроме намеренного обнуления при смерти (`hunt_result._apply_defeat`, GDD 1.3).

Причина та же, что у §13.1: «хватает ли монет» решалось **в четырёх копиях** —
оружие, броня и совет в экране города плюс покупка в прогоне баланса. Пока копии
совпадали, всё работало; разойтись они могли в любой правке. Отдельно опасна
форма «проверить здесь, списать следом»: если побочные действия (выдать оружие,
записать навык) стоят вне ветки отказа, игрок получает товар бесплатно. Именно
так выглядела бы ошибка, и она **воспроизведена для проверки** — проверка
покраснела строкой «кошелёк 14 (был 14), оружия 3 (было 2)».

Экономику стерегут **две** проверки, и обе нужны:

| Где | Что проверяет |
|---|---|
| `--ui` → `_economy_check` | настоящий обработчик кнопки города: отказ при нехватке, успех ровно впритык |
| `--loop` | инвариант за прогон: кошелёк не уходил в минус **и** траты вообще были |

Второе условие в `--loop` не украшение. Проверка «монеты не ушли в минус» зелена
и на прогоне, где не куплено ничего, то есть не проверилось ничего — тот же
порожняк, что был у строкового рендера досье.

**Чего `--loop` НЕ проверяет, и это выяснено опытом:** со снятой защитой внутри
`spend_coins` прогон остался зелёным, потому что симулятор спрашивает
доступность снаружи (`can_afford`). Путь экрана прогон не трогает вовсе — поэтому
и понадобилась отдельная проверка в `--ui`.

### 13.4 Статусы и туман: обещание в тексте обязано быть выполнимым

Один класс ошибок, три случая, и все три жили в игре незамеченными:

| Что обещали | Что было в коде |
|---|---|
| «зверь слепнет» (комбо Пепел-Матери и Шипуна) | слова `blind` не было **ни в одном файле** |
| «зверь открыт на 2 хода» (комбо Тлеуна) | слова `open` не было **ни в одном файле** |
| «ТУМАН ОБЗОРА» (карточка досье Тлеуна) | `fog_active` уходил только в арт — затемнял картинку, а прозу и улики не трогал |

Игрок тратил ход на комбо, читал описание эффекта и не получал ничего. Это тот же
разъезд «подпись против механики», что и с типом урона (§13.1), только вместо
подписи — текст эффекта.

**Что сделано.** Три механики внедрены, а список статусов движка стал явным:
`BattleEngine.STATUS_IDS` — единственный источник того, что движок умеет.
Валидатор сверяет с ним контент и **ловит четвёртый такой случай заранее**: опечатка
в `status_id` или недоделанная механика больше не пройдут молча. Проверка сначала
покраснела на живом контенте — три нарушения, поимённо.

**Как работают механики.**

- `blind` — слепнет **зверь**, он не подаёт знаков. Проза раунда остаётся без улик.
- `open` — зверь пропустил защиту, любой удар идёт на 1 глубже. Отдельное слагаемое
  `DamageResult.open_bonus`, а не добавка к типовому множителю: открытость не про тип
  урона, и складывать её с уязвимостями значило бы обещать в разборе то, чего нет.
- туман — скрывает улики **от игрока**. Скрытие сделано одним рычагом: когда читать
  нечего, `advance_round()` снимает строки прозы и кладёт готовый текст вместо них.
  Отдельной проверки статусов в `_core_signal_labels()` **нет намеренно** — второй
  механизм для того же самого стал бы вторым источником правды и однажды вернул бы
  улики в досье «через чёрный ход».

**Почему скрывается всё, а не только подсветка.** Обсуждался мягкий вариант (гасить
подсветку навыков, оставляя текст улик). Выбрано полное скрытие: туман у Тлеуна
должен быть загадкой, а не ослаблением привычки. Верное чтение ключевого сценария
туман рассеивает, и со следующего раунда улики возвращаются.

**Замечено, но НЕ сделано:** `fog_text` из контента («Туман осел. Ты снова видишь…»)
написан как сообщение о **рассеивании**. В состоянии «ничего не видно» он читался бы
противоположно смыслу, поэтому в тумане показывается своя формулировка, а `fog_text`
ждёт момента, когда туман снимается.

## 14. Арт: слот, который работает без картинок

Арт живёт в `ui/components/art_slot.gd` и **не влияет на ядро вообще**: движок отдаёт
сценарий, слот сам решает, что показать. Это позволяет добавлять графику поштучно,
не пересобирая игру.

Пути к фонам и порядок расширений — в `core/ui_data/art_paths.gd` (`ArtPaths`).
Файл вынесен из `CityData` намеренно: ни один расчёт баланса к картинкам не
обращается, поэтому таблица путей не должна лежать среди заказов и цен.

Три решения, которые стоит сохранить при доработке:

1. **Запасной режим обязателен.** Если текстуры нет, слот рисует подпись вида цветом
   акцента. Игра остаётся читаемой на любом виде, даже ненарисованном, — поэтому арт
   можно добавлять в любом порядке.
2. **Поза берётся из сценария.** `MonsterData.by_scenario` — это `{"сценарий": текстура}`,
   и связь бесплатная: состояние зверя уже есть в ядре (GDD 3.2 называет позу
   визуальным слотом). Никакого нового слоя данных не понадобилось.
3. **Формат — SVG.** Текстовый, диффится в git, масштабируется без потерь. Импорт
   с `svg/scale=2.0` даёт 1024x1024 на карточку и 1024x576 на фон.

Две ловушки формата `.tres`, на которые я наступил при подключении арта:

- **`Color("#7a6849")` в ресурсе не парсится.** Godot ждёт числовой конструктор
  `Color(r, g, b, a)` и падает с «Expected float in constructor». Решение: хранить
  цвет **строкой** и конвертировать методом `accent()` — так в данных остаётся
  читаемый hex.
- **`Vector2(0,10)` тоже падает.** Нужен пробел после запятой: `Vector2(0, 10)`.

Общее правило: **`.tres` — не JSON, его конструкторы придирчивы к пробелам.**
После правки ресурсов руками всегда прогонять `--import` и смотреть stderr:
`load()` вернёт null молча, а причину покажет только лог импорта.

## 15. Досье: один сборщик на игру и на прогон

`DossierRecorder` вынесен отдельно после того, как smoke-тест показал досье пустым:
сбор фактов жил только внутри экрана боя, поэтому симулятор полного цикла собирал
их собственной копией кода. Две реализации одной логики означают, что прогон
прогрессии перестаёт быть проверкой игры.

Правило: если логика нужна и экрану, и симулятору — она живёт в `core/`, а экран
её только вызывает. То же касается применения прогрессии: `HuntResult.apply`
вызывается из корневого узла, а не из экрана боя.

### 15.1 Досье показывает не улики, а «какая улика про какую атаку»

Первая версия досье печатала два независимых списка: «Опорные сигналы» и
«Сценарии». Игрок видел набор улик и набор атак, но связать одно с другим мог
только заучив соответствие по боям. Это отвечает на вопрос «что я видел», а не на
тот, ради которого досье открывают: «что мне делать с тем, что я видел».

Связь при этом **уже была в контенте**: каждый сигнал несёт `scenario_id`, и
валидатор требует этого как инвариант. То есть досье не нужно было выдумывать
связь — её нужно было перестать терять при отображении. Теперь атака это
заголовок, а её улики идут под ней.

### 15.2 Окно вида: структура в core, показ в компоненте

Строковый рендер вырос в портянку: у вида с тремя атаками это 600+ пикселей
текста, и низ экрана уезжал за кадр. Замена — отдельное окно вида
(`ui/components/dossier_window.gd`), которое открывают **три** экрана: город,
подготовка и бой (в бою — по навыку «Досье в бою», один раз за бой). Одно окно на
три места — не экономия, а условие: две реализации досье уже расходились в этом
проекте.

**Структуру собирает core.** `DossierText.dossier_view(mon)` возвращает словарь
(identity, stats, attacks, special, weaknesses, resists, unlearned), а окно только
рисует. Причина не в красоте: строки проверяются лишь глазами, а структуру можно
проверить прогоном — «у каждой атаки её улики», «особые правила не потерялись».
Это тот же принцип, что и с `DossierRecorder`: логика в `core`, экран её зовёт.

**Раскладка: слева зверь, справа поведение.** Слева портрет, числа, уязвимости,
резисты и особые правила; справа атаки во всю ширину. Порядок именно такой,
потому что в узкой колонке (595 px) описания переносятся и три атаки Хруза
занимают ~800 px — прокрутка возвращается. Во всю ширину (812 px) тот же разбор
укладывается в ~525 px и виден целиком. Лор живёт справа под заголовком.

**Неизученная атака остаётся на своём месте ЗАКРЫТОЙ.** Название, описание,
улики, обманы, комбо и урон заменяются знаками вопроса (`?????? ???????`,
`бьёт на ?`), а внизу стоит «Закрыто атак: N». Показывать такую атаку целиком
нельзя — это и есть то, что игрок покупает боями. Выбрасывать из списка тоже
нельзя: тогда пропадает и счёт, и ощущение «здесь есть что открыть».

**Частота атак НЕ показывается.** Веса сценариев — внутренняя механика: решение
по дизайну, что игрок читает поведение по уликам и по боям, а не по проценту,
который ему выдали. Поэтому в структуре окна нет поля `chance`, а
`ScenarioData.chance_percent()` помечен как внутренний (им пользуется только
отчёт `--prose`, где баланс проверяют глазами). Соблазн вернуть процент велик —
он делает разбор «полезнее» на вид, — поэтому правило записано здесь и в самом
методе.

**Описания атаки в досье НЕТ.** `ScenarioData.description` сначала выводилось под
заголовком атаки, и это оказалось вредным. Описание дословно повторяло
формулировки опорных сигналов: «Припадает к земле и обрушивается всем весом»
против сигнала «припадает к земле». Игрок читал описание как подсказку и ждал в
прозе именно этого признака, а проза выдаёт **один** сигнал из списка — возможно,
другой. Строка была одновременно бесполезной (предсказать по ней нечего, она
статична) и обманчивой (учила ждать не тот признак). Поле осталось в
`ScenarioData`: оно нужно разбору после боя. Урок общий — рядом стоящие фразы
обязаны иметь разные роли, иначе игрок принимает одну за другую.

**Слева под портретом — особые правила (GDD 5.6, уровень «Анализ»).** Туман
обзора, тлеющий урон, фазы, привыкание и контр-приём. Данные для них лежали в
виде с самого начала (`fog_*`, `ticking_*`, `phases`, `adaptations`), но их не
читал ни один экран — в досье этих правил просто не было.

**Почему обман показан под конкретной атакой.** Не по смыслу, а механически:
`TextGenerator` подмешивает в прозу сценария опорные сигналы ЭТОГО сценария плюс
ложные следы с тем же `scenario_id` (общие следы вида с пустым `scenario_id`
добирают бюджет). Значит обман звучит в абзаце той атаки, которую маскирует, — и
досье, ставя его под эту атаку, говорит ровно нужное: «увидишь эту фразу — она про
эту атаку, и она лжёт». Общий список «ложные следы: …» этого не сообщает: он лишь
перечисляет, что тебя когда-то обмануло, и сопоставлять с атакой игроку придётся
заново — то есть делать ту работу, ради которой он досье и открыл.

Второе следствие: обман и опорные сигналы одной атаки **конкурируют за слот**.
Валидатор запрещает обману занимать слот опоры своего сценария (иначе в прозе две
фразы про `[поза]` и опору не отличить от лжи). Под атакой это видно глазами.

**Общие обманы (`scenario_id == &""`) остаются без своей атаки.** Они могут
подмешаться в прозу любой, поэтому «своей» атаки у них нет физически — и они
печатаются отдельной строкой «Обманы без своей атаки». Важно: сейчас таких в
контенте НЕТ (проверены все 55 обманов у семи видов — у каждого есть сценарий),
поэтому без этой ветки потеря прошла бы незамеченной ровно до того дня, когда
контент её завёл бы.

**Проверка.** Связка «улика в блоке своей атаки» проверяется headless режимом
`--prep` на живом экране и валидатором контента — по **всем** видам сразу, на
полном наборе знаний. Один вид может совпасть случайно, шесть подряд — нет.
Валидатор при этом сохраняет и возвращает досье игры: проверка не имеет права
оставлять след в состоянии забега.

Грабли проверки в живой игре: одиночное нажатие через MCP не срабатывает, нужна
**последовательность** «движение → нажатие → отпускание» с задержкой (~60 мс).
Отдельные `simulate_mouse` события кнопку не нажимают, хотя счётчик `injected`
растёт — то есть события доходят, но `pressed` не срабатывает.

## 16. Инструменты разработки: MCP и аддон godot_mcp
**Зачем.** До этого игра проверялась только снаружи: headless-прогоны, отчёты
в файлах, замер пикселей через System.Drawing. Это ловило логику, но не давало
ни увидеть игру, ни нажать в ней кнопку, ни спросить живое состояние.

**Что подключено.** MCP-сервер `godot-editor-mcp` (он же godot-mcp, MIT,
`pip`/`uvx`, Godot 4.4+), который водит **живой редактор** через аддон:

```
DSH → @deepseek-ai/dsh-mcp-client → uvx godot-editor-mcp
    → мост ws://127.0.0.1:9080 ← аддон godot_mcp в редакторе
```

- Конфигурация клиента — в патче профиля DSH
  (`~/.dsh/profiles/web/cordis.patch.yml`), **не в проекте**.
- `command` указывает на `uvx.exe` полным путём: pip поставил uv в
  пользовательскую схему (`%APPDATA%\Python\Python314\Scripts`), а этот каталог
  в PATH не прописан.
- Аддон лежит в `addons/godot_mcp/` и включён в `project.godot`
  (`[editor_plugins]`).
- `mcp_runtime_probe.gd` добавлен **автозагрузкой** — без него MCP не видит
  запущенную игру: не может ни снять кадр, ни нажать кнопку. Пробник безопасен:
  всё, что он делает, стоит под `EngineDebugger.is_active()`, то есть вне
  отладочного запуска (и в экспортированной сборке) он не работает вовсе.

**Что это даёт на практике** (проверено, а не по документации):

| Задача | Инструмент |
|---|---|
| Убедиться, что проект запускается без ошибок | `run_and_capture` |
| Проверить GDScript на ошибки парсинга | `scripts_get_parse_errors` |
| Посмотреть живое дерево сцены | `get_game_scene_tree` |
| Найти кнопку и нажать её | `find_ui_elements` + `simulate_mouse` |
| Прочитать, что игра показывает сейчас | `find_ui_elements` (тексты узлов) |
| Быстро проверить `run/main_scene`, автозагрузки | `get_project_info` |

**Как устроен доступ.** Наборы инструментов (29 штук) включаются по одному;
по умолчанию открыты только `core` и `inspection` — чтение. В этой сессии
включены дополнительно `scripts`, `runtime`, `editor`, `testing`, `input`.
Мутирующие наборы (`scene_edit`, `resources_edit`, `export`) остаются закрытыми
намеренно: правки игры делаются текстом, а не через редактор.

**Как отключить.** Убрать запись `mcp-godot` из патча профиля и перезапустить
DSH. Аддон и автозагрузку можно оставить: без сервера пробник не активируется.
Если убирать полностью — удалить `addons/godot_mcp/`, строку
`MCPRuntimeProbe` из `[autoload]` и запись из `[editor_plugins]`.

**Известная поломка: скриншоты через MCP не работают.** Попытка снять кадр даёт
в редакторе ошибку движка:

```
ERROR: modules/websocket/wsl_peer.cpp:790 -
Condition "outbound_buffer_size > 0 && (wslay_event_get_queued_msg_length(wsl_ctx)
+ p_buffer_size > (uint32_t)outbound_buffer_size)" is true. Returning: ERR_OUT_OF_MEMORY
```

Это **переполнение исходящего буфера WebSocket на стороне аддона**: пробник
кодирует кадр в PNG, затем в base64 (`Marshalls.raw_to_base64(image.save_png_to_buffer())`)
и отправляет одним `send_text`. Кадр 1280×720 — сотни килобайт, а `WebSocketPeer`
в аддоне создаётся как `WebSocketPeer.new()` без настройки буфера отправки.
Мелкие сообщения (команды, ответы, состояние) проходят нормально — ломаются
только кадры. Починки на нашей стороне нет: размер буфера задаётся до подключения.

**Обход: снимать кадр самим, без сокета.** Режим `-- --shots` играет игру в
процессе и сохраняет PNG прямо с вьюпорта в `_shots/`:

```powershell
& $godot --path F:\WORK\hunter -- --shots
```

Именно поэтому режим существует: он не зависит ни от аддона, ни от размера
буфера. Запускать **с окном** (не `--headless`): в headless-режиме нет
визуального вьюпорта, и кадр сохранять нечего. Режим наполняет ношу добычей,
чтобы на снимке были видны списки и кнопки рынка, а не только пустое состояние.

## 17. Грабли этой среды (проверено на практике)

- **`preload()` ломает точку входа.** Если `main.gd` парсит отсутствующий файл,
  `_ready()` не выполняется, `quit()` не вызывается и Godot висит вечно.
  Поэтому все внешние скрипты в `main.gd` грузятся через `load()`.
- **`.tres` вложенные ресурсы.** Порядок ссылок выяснен пробником `--probe`:
  `signals = Array[ExtResource("<script>")]([SubResource("id"), ...])` — в типе
  массива стоит **скрипт**, а не `Resource`.
- **Ошибки парсинга скрипта сцены в headless не печатаются.** Молчаливый провал
  выглядит как «ничего не произошло». Диагноз ставится только явным тестом.
- **Предупреждения = ошибки.** `var x := dict.get(...)` падает с parse error.
  Нужен явный тип: `var x: Array = dict.get(...)`.
- **Пайп в этой среде бывает недоступен.** Все отчёты пишутся файлами.
- **Перенаправление stdout подвешивает запуск.** `Start-Process -RedirectStandardOutput`
  (и вообще любой захват вывода) ждёт закрытия канала, которого не происходит:
  процесс выглядит бесконечно висящим, вывод пуст, ошибок нет. Проверено на
  `--version`, который обязан завершаться мгновенно, — висел точно так же.
  Диагноз ставится сравнением: тот же запуск **без** перенаправления завершается
  с кодом 0. Практическое правило: запускать режимы без перенаправления, а
  результат читать из файла отчёта, который пишет сам Godot через `FileAccess`.
  Именно поэтому `--validate` тоже пишет `_validate_out.txt`, а не только `print()`.
- **Открытый редактор — НЕ помеха headless-прогонам.** Раньше здесь стояло
  обратное утверждение («пока запущен редактор, headless молча не стартует»), и
  оно **неверно**. Проверено напрямую: при открытом редакторе
  `--headless --path F:\WORK\hunter --quit-after 2` завершается с кодом 0.
  Настоящая причина «молчаливого зависания» — потерянный разделитель `--`
  (см. ниже). Ложный вывод стоил нескольких запусков и одной снесённой сессии
  редактора, поэтому важно: диагноз ставится экспериментом, а не догадкой.
- **`.ps1` и `.cmd` в этом проекте пишутся ТОЛЬКО на ASCII.** Windows PowerShell
  5.1 (`powershell.exe`, не `pwsh`) читает `.ps1` без BOM как кодовую страницу
  1251, поэтому русские комментарии в скрипте превращаются в мусор и ломают
  парсер: `Отсутствует закрывающий знак "}" ... MissingEndCurlyBrace` на строках,
  где синтаксис в порядке, а в тексте ошибки видно `(С…РІРѕСЃС‚)` вместо «хвост».
  Та же беда у `.cmd`: `cmd.exe` читает файл в OEM-кодировке, и покорёженный
  `REM` способен «съесть» следующую строку. Это уже вторая форма одной грабли
  «PowerShell портит UTF-8» (первая — запрет на `Set-Content` для текстов проекта).
  Правило: в `tools/` комментарии и сообщения по-английски; русский текст из
  скрипта не печатать, а читать из файлов-отчётов, которые пишет сам Godot.
- **Режим обязан идти ПОСЛЕ `--`, иначе прогон «висит на старте».** Godot считает
  флаг без разделителя своим, `OS.get_cmdline_user_args()` остаётся пустым,
  `main.gd` не находит режима и уходит в `_open_game()`. В headless это вечная
  игра без окна: ни вывода, ни отчёта, ни `quit()` — снаружи неотличимо от
  «движок сломался после падения». Правильно:

  ```powershell
  & $godot --headless --path F:\WORK\hunter -- --validate --log-file F:\WORK\hunter\_glog.txt
  ```

  Проверено сравнением: без `--` процесс живёт бесконечно и отчёт не появляется,
  с `--` режим отрабатывает и пишет отчёт. Признак именно этой ошибки: в логе
  только баннер движка и `Failed to read the root certificate store`, а
  `_ready()` не выполнена (никаких вех и отчётов).
  Запускать проверки через `tools\run_checks.cmd`: он ставит `--` сам, добавляет
  `--quit-after 2000` как страховку от вечного цикла и печатает отчёты.
- **Не убивать процессы Godot по имени или по времени старта.** Редактор и
  прогоны — один и тот же образ (`Godot_v4.7.2-stable_win64.exe`), поэтому
  отличить их по имени нельзя, а время старта обманывает: осиротевший прогон и
  редактор легко меняются местами. Дважды подряд это привело к сносу редактора
  вместо прогона. Правило: смотреть командную строку (`-e`/`--editor` — редактор)
  и только затем бить по конкретному PID; в сомнении — не бить вовсе.
- **Кнопка в живой игре нажимается только последовательностью.** Отдельные
  `simulate_mouse` (нажатие, потом отпускание двумя вызовами) доходят до игры —
  счётчик `injected` растёт — но `pressed` не срабатывает: текст кнопки не
  меняется. Работает `play_input_sequence` из трёх событий: движение в точку,
  нажатие, отпускание, с `delay_ms` около 60. Проверено на кнопке «ДОСЬЕ»:
  последовательность открыла и закрыла досье, одиночные клики — нет.
- **Временную обёртку для проверки экрана надо удалять.** Чтобы поднять экран
  подготовки без похода по игре (город -> заказ -> тропа), создавался
  `_prep_harness.tscn` с `setup_location(Database.monster(&"hruz"))`. После
  проверки он удалён: забытая обёртка — это второй вход в игру, который никто не
  поддерживает.
- **`Get-Process *odot*` — ловушка: под маску попадает MCP-сервер.** Имя
  `godot-editor-mcp` содержит «godot», поэтому массовое снятие процессов по этой
  маске убивает не только редактор, но и рабочий MCP-сервер (он перезапустится,
  но это лишний шум и потерянное время). Искать процессы по точному имени:
  `Get-Process Godot_v4.7.2-stable_win64, Godot_v4.7.2-stable_win64_console`.
- **Нельзя править текст через `Get-Content`/`Set-Content`:** PowerShell читает
  UTF-8 как CP1251 и портит файл. Только `edit`-инструмент или .NET с явным UTF-8.
- **`run/main_scene` — это точка входа, а не «какой экран показать».** Однажды
  переключение `main_scene` на `game_root.tscn` (чтобы играть) сломало все
  headless-режимы: `quit()` живёт в `main.gd`, поэтому Godot начал висеть вечно
  без единой ошибки в логе. Точка входа всегда `main.tscn`, а игру открывает
  `main.gd` через `_open_game()`.
- **«Ничего не произошло» — самый дорогой симптом.** Когда нет ни вывода, ни
  ошибки, единственный способ разобраться — писать вехи в файл на каждом шаге.
  Так нашлись и вечное зависание из-за `main_scene`, и пустое досье.
- **Читать ошибки движка через `--log-file` — главный инструмент диагностики.**
  Godot печатает ошибки скриптов в stdout, а stdout в этой среде не поймать
  (пайп виснет, `-RedirectStandardOutput` подвешивает процесс). Решение —
  собственный лог движка:

  ```powershell
  & $godot --headless --log-file F:\WORK\hunter\_glog.txt --path F:\WORK\hunter -- --loop 10
  ```

  В `_glog.txt` попадают `SCRIPT ERROR`, `Parse Error` и трассировки стека
  с номерами строк. Так нашлась ошибка, которую иначе было не видно:
  `Function "empty()" not found in base Dictionary` — у `Dictionary` в GDScript
  нет метода `empty()`, есть `is_empty()`. Неверный вызов не давал **ни одной**
  ошибки в отчётах: файл не компилировался, зависимый скрипт падал следом, и
  прогон просто вырождался в четыре строки. Ни отчёт, ни трассы `FileAccess`
  этого не показывали — показал только лог движка.
- **Вырожденный отчёт — признак ошибки компиляции, а не пустых данных.**
  Если прогон завершается кодом 0, а отчёт короче обычного, первым делом смотреть
  `--log-file`: скорее всего один из скриптов не скомпилировался, и режим упал
  на `load()`. Подозреваемое место — новые вызовы методов у встроенных типов.
- **`load_steps` в шапке `.tres` обязателен и должен быть точным.** Если добавить
  подресурсы, а число не пересчитать, ресурс молча не загрузится: `load()` вернёт
  null без внятной ошибки в логе. Пересчитывать как `ext_resources + sub_resources + 1`.
- **Любая ссылка `SubResource("x")` без определения роняет весь файл.** Одна
  обрезанная строка `id = &"gromun.decoy.roar."` сделала нечитаемыми все пять
  видов сразу. Полезная проверка перед запуском: собрать все `SubResource("...")`
  и убедиться, что каждому есть `[sub_resource ... id="..."]`.
- **Не писать контент генератором, который правит файл по границам блоков.**
  Я потерял блоки сценариев и комбо у трёх видов, потому что они лежали ПОСЛЕ
  блоков обманов, а мой скрипт заменял «от первого обмана до `[resource]`».
  Правило: если файл правится программно, либо переписывать его целиком из
  спецификации, либо сохранять всё, что не размечено явно.
- **`Set-Content`/`Get-Content` и построчный разбор в PowerShell** дважды
  испортили файлы и один раз уронили сам PowerShell (переполнение стека в
  самодельном CSV-парсере, код 0xC0000409). Для текстовых файлов — только
  `edit`-инструмент или .NET с явным UTF-8; для CSV внутри текста — корректный
  квотинг (текст с запятыми обязан быть в кавычках, кавычки внутри — удвоены).
