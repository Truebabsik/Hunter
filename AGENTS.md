# Указания для агента

Проект **ОХОТНИК** — прототип пошагового рогалика о чтении монстров на Godot 4.7.2.
Этот файл лежит в корне проекта и версионируется вместе с кодом: правило, которое
живёт вне репозитория, теряется при первой попытке работать с проектом в другом месте.

---

## 1. Перед любой правкой кода — загрузить скилл `godot-4-development`

**Всегда, когда правишь код в проекте, сначала вызывай скилл `godot-4-development`.**
Это правило пользователя, а не рекомендация.

Скилл лежит локально: `F:\WORK\.dsh\skills\godot-4-development\SKILL.md`.
Он собран по официальной документации Godot 4 и покрывает: рендереры, узлы и классы,
GDScript, GUI, анимацию, физику, звук, ввод, навигацию, файлы и сохранения, экспорт,
а также типовые ошибки и их причины.

Что это значит на практике:

- «код» — это не только `.gd`, но и `.tres`/`.tscn`, `project.godot`, скрипты проверок
  и инструменты в `tools/`;
- версия проекта — **Godot 4.7.2**, приём из туториалов 3.x не подходит: там другие
  рендереры, `TileMap`, синтаксис GDScript и работа с `Input`;
- в скилле есть раздел с частыми ошибками (пустой ресурс, не подхватился импорт,
  сигнал не сработал). Прежде чем искать причину наугад — сверить с ним;
- обжог световых карт (`LightmapGI`) и генерация навигационной сетки требуют
  **редактора**, а не `--headless`. Весь рабочий цикл проекта — headless.

## 2. MCP-сервер для Godot

К проекту подключён **`godot-mcp`** (аддон `addons/godot_mcp`, MCP-сервер поверх
редактора). Он нужен для того, чего не умеет headless: **заглянуть в живой
редактор** — дерево сцены, свойства узлов, выделенный узел, открытые сцены.

Проверенное состояние (сверено, а не по памяти):

- версия сервера **2026.09.23**, протокол stdio, мост `ws://localhost:9080` — подключён;
- подключён именно наш проект: `ОХОТНИК`, `F:/WORK/hunter`, Godot 4.7.2, открыта `main.tscn`;
- инструменты появляются в сессии с префиксом `mcp__godot__*`.

**По умолчанию включены только два тулсета: `core` и `inspection`.** Остальные
(scene_edit, runtime, scripts, resources_edit, project, testing, editor, debugger и ещё
два десятка) надо включать явно: `enable_toolset("scene_edit")`. Иначе инструмент
не найдётся — это не поломка, а экономия контекста. Включённый тулсет стоит гасить
обратно (`disable_toolset`), чтобы не держать лишние инструменты в сессии.

Полезное для нас:

- `inspection_*` — дерево сцены, свойства узла, список сцен, выделенный узел.
  **Работает без запуска игры** и без правок: можно посмотреть, что реально собралось.
- `testing_run_test_scenario` — проиграть сцену, подать ввод и проверить свойства
  живого узла. Это дополняет наши headless-проверки, но **не заменяет их**: наши
  режимы покрывают логику без сцен, а этот работает по сценам и требует живого сеанса.
- `undo` / `redo` — правки, сделанные через MCP, идут через историю редактора,
  поэтому откатываются штатно.

**Чего MCP не может — и это проверено:**

- **снимок экрана не работает.** `editor_capture_screenshot` отвечает
  `TIMEOUT: No response from Godot within 10.0s`. Причина в аддоне: буфер WebSocket
  переполняется на большом PNG (`wsl_peer.cpp: ERR_OUT_OF_MEMORY`), и кадр не доходит.
  Поэтому **вёрстку проверяем не снимком, а замером прямоугольников** (`--ui`) —
  и помним, что про внешний вид экрана мы знаем только по числам;
- **живые инструменты требуют сеанса игры.** `input`, `runtime`, `debugger` и
  `testing_run_stress_test` просят активный play-сеанс. Автолоад `MCPRuntimeProbe`
  в `project.godot` уже прописан, так что `play_scene()` их включает;
- **`godot_debug_workflow` — не замена нашим режимам.** Он запускает main-сцену
  (`--headless --path`, без аргументов после `--`), то есть игру без выхода, и
  завершается по таймауту. Наши режимы запускаются иначе и пишут отчёты файлами.

Практическое следствие: **MCP — для осмотра и живого сеанса, наши режимы — для проверок.**
Не тащить проверки в MCP и не пытаться смотреть вёрстку снимком через него.

## 3. Проверять фактом, а не галочкой

В проекте нет фреймворка тестов: проверки — это headless-режимы движка.
Они пишут отчёты файлами, поэтому читать надо **отчёт**, а не вывод консоли.

```
tools\run_checks.cmd                    # все режимы
tools\run_checks.cmd --prep --validate  # отдельные
```

Правила, добытые дорого (подробности — `README.md`, «Грабли, которые стоили времени»,
и `docs/ARCHITECTURE.md`):

- **зелёная проверка ничего не значит, пока не показано, что она умеет краснеть.**
  Прежде чем объявлять работу сделанной, сломай то, что она сторожит, и убедись,
  что она это назвала;
- **красная проверка тоже ничего не значит, пока не показано, что она краснеет
  на ДОСТИЖИМОМ состоянии.** Дважды за сессию проверка краснела на состоянии,
  которое игра создать не может: тест сам вписывал противоречивые данные и находил
  «дефект» в себе;
- **стухший отчёт выглядит как успех.** Если режим упал до записи, на диске остаётся
  прошлый файл. Перед прогоном отчёты удаляются — не полагайся на файл неизвестного
  возраста;
- **симулятор тоже врёт.** Он может считать не ту игру (например, выдавать боту
  несозданное оружие) и показывать числа, которых в игре нет;
- `--` перед режимом **обязателен**: без него Godot примет флаг как свой, `main.gd`
  не найдёт режим и запустит игру без выхода;
- **отчёты не версионируются** (см. `.gitignore`): они стареют молча, и в репозитории
  устаревший отчёт выглядит как свидетельство о том, чего уже нет.

## 4. Границы слоёв

- `core/` — чистая логика без `Node`, `SceneTree` и сцен: она обязана работать headless.
  Числа живут константами, решения принимают чистые функции;
- `ui/` — только показ и нажатия. Если экран начинает **решать** правила боя, экономики
  или досье — это ошибка размещения, а не стилистика;
- один источник на каждое правило. Копия правила в двух местах расходится молча:
  в этом проекте так уже разъезжались названия типов урона, формулы навыков,
  цена совета и гейт достижения.

**Отдельно про контент:** если текст что-то обещает («зверь слепнет», «зверь открыт»,
«ТУМАН ОБЗОРА»), механика обязана это выполнять. Три таких обещания уже жили в игре
без исполнения. Валидатор сверяет статусы комбо со списком `BattleEngine.STATUS_IDS`.

## 5. Git

Репозиторий — в корне проекта (`F:\WORK\hunter`), ветка `main`.
Идентичность коммитов задана локально (`hunter-dev@localhost`): глобальные настройки
git на машине пусты, без них коммит не создаётся.

Не версионируются: `.godot/` (кэш импорта), `addons/godot_mcp/` (чужой код, автор
hybridindie), отчёты проверок и `sim_report.json` (генерируются, стареют молча).
Версионируются `.import`-файлы арта: в них параметры импорта, в том числе `svg/scale`.
